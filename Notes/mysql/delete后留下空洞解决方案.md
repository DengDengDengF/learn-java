# DELETE 后留下空洞：原理与解决方案

> 适用引擎：InnoDB。本文说明为什么 DELETE 删完磁盘空间不释放、空洞能不能被复用、以及如何判断与回收。

---

## 一、DELETE / TRUNCATE / DROP 对数据与空间的区别

三个命令都会删数据，区别在于“删多少”“表壳还在不在”“空间还不还给系统”。

| | DELETE | TRUNCATE | DROP |
| --- | --- | --- | --- |
| 类型 | DML | DDL | DDL |
| 删除粒度 | 逐行（支持 `WHERE`） | 整表数据 | 整个表对象 |
| 表结构 | 保留 | 保留 | 删除 |
| 可回滚 | ✅ 事务内可 | ❌ | ❌ |
| 自增值 | 不重置 | 重置 | 表都没了 |
| **磁盘文件大小** | **基本不变** | **立即变小** | **立即变小** |
| 空间去向 | 变成表内可复用空洞，不还给系统 | 删旧文件建新空文件，还给系统 | 表文件整个删除，还给系统 |

- 删**一部分**数据只能用 `DELETE ... WHERE`（另两个不支持条件）。
- 清空**整表**且想立刻回收空间，用 `TRUNCATE` 比 `DELETE` 强得多。
- DELETE 的“保留”指保留**表结构（壳）**，不是保留数据；数据是真删掉的。

---

## 二、DELETE 后空间去哪了：标记删除，不还给系统

```sql
DELETE FROM user WHERE status = 0;   -- 删了很多行
```

删完磁盘上的 `.ibd` 文件大小**基本没变**。InnoDB 的处理是：

1. 把这些行标记为“已删除”。
2. 它们占的空间变成**可复用的空闲空间**，留在原来的数据页里。
3. 文件**不缩小**，空间**不还给操作系统**，只能被这张表后续的写入复用。

```
删除前:  [■■■■■■■■■■]  文件 1GB，全是数据
删除后:  [■■□□□□□□■■]  文件还是 1GB，□ 是可复用空洞，磁盘没空出来
```

这种“文件里全是空洞、数据稀疏”的现象叫**碎片（fragmentation）**。

### 为什么这么设计

- 立即收缩文件代价极高：要移动大量数据、重排页、改所有索引，DELETE 会慢到不可接受。
- MVCC 需要：被删的行可能还有别的事务在用（旧版本），得等 purge 线程后台清理。
- 大概率还要写入：删了马上又插，留着空间复用效率更高。

---

## 三、空洞能不能被复用：看“键值落在哪个页”，不是插入顺序

InnoDB 的聚簇索引按**主键排序**存放，一条新行插到哪个页**由它的主键值决定**，而不是“哪个洞先空出来就从前往后填”。

```
主键顺序排列的页:
[页A: id 1~100] [页B: id 101~200] [页C: id 201~300]

删掉 id 101~200 → 页B 变成空洞
插入 id = 50000 → 属于表尾，去新页，页B 的空洞继续空着！
```

因为 `id = 50000` 不落在页B的 101~200 区间，就不会去填页B。**键值不落在空洞所在页的区间，那个洞就继续空着。**

二级索引同理：按索引列的值定位，新行该列的值落在哪个页，才可能复用那个页的空洞。

### 自增主键表的典型现象（重点）

`AUTO_INCREMENT` 计数器**只增不回退**，不会因为你删了中间 id 就退回去。

```sql
DELETE FROM user WHERE id BETWEEN 101 AND 200;  -- 中间挖洞
INSERT INTO user(name) VALUES ('x');            -- 新 id = 1001，去表尾
-- 中间 id 101~200 的空洞，普通 INSERT 永远填不回！
```

**结论：对自增主键表，删掉中间段数据后，页内零散空洞在正常使用下基本永久空着，无法通过普通 INSERT 填回。**

> 注：手动指定 id 插入（`INSERT INTO user(id,...) VALUES(150,...)`）或 `UPDATE` 改主键，理论上能落进旧区间复用空洞，但都是**非常规、不推荐**的操作，实践中不会为填空洞而这么做。

---

## 四、唯一能被正常复用的情况：整页空闲

空间复用分两个层级：

| 层级 | 谁能复用 | 受什么限制 |
| --- | --- | --- |
| **页内空洞**（删几行，页没空） | 本页 | 新行键值必须落在**这个页的区间**，否则空着 |
| **整页空闲**（页被删空或半空页合并） | 整个表空间 | **不限区间**，任意新数据可用，但仍不还给 OS |

- 当你删的是**整个页的连续数据**（如连续一大段 id），这个页会整个空出来，进入表空间的**空闲页列表**，后续任何新数据（包括大 id 追加）都能复用它。
- 当相邻页填充率都很低（默认低于约 50%，受 `MERGE_THRESHOLD` 控制），InnoDB 会**合并相邻半空页**，腾出的整页也进空闲列表。
- 但无论哪种，腾出的页只回到**本表空间**，**不还给操作系统**，文件大小照样不缩小。

## 五、如何判断空洞有多大

**先量化再决定**，碎片小就别折腾。

```sql
SELECT
  TABLE_NAME,
  ROUND(DATA_LENGTH  / 1024 / 1024)                        AS data_mb,   -- 实际数据
  ROUND(DATA_FREE    / 1024 / 1024)                        AS free_mb,   -- 空洞大小
  ROUND(DATA_FREE / (DATA_LENGTH + INDEX_LENGTH) * 100, 1) AS frag_pct   -- 碎片率%
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'your_db' AND TABLE_NAME = 'user';
```

| 碎片率 | 处理建议 |
| --- | --- |
| < 10% | 别管，正常现象，会被复用 |
| 10% ~ 30% | 留意，择机整理 |
| > 30% 或 free_mb 达数 GB | 值得回收 |

**心态：碎片 ≠ 问题。** 表若还在频繁写入，空洞会被复用，整理了也会很快再产生。只有“删了一大批且之后写得少”的表才真正需要处理。

## 六、如何回收空洞、缩小文件

### 方案 A：OPTIMIZE TABLE（最常用）

```sql
OPTIMIZE TABLE user;
```

本质是重建整张表：数据紧凑重写、丢掉空洞、空间还给系统。InnoDB 下等价于 `ALTER TABLE ... ENGINE=InnoDB`。

**代价（务必清楚）：**
- 会锁表 / 重建表，大表期间影响读写，可能很慢。
- 需要**额外磁盘空间**（重建时新旧文件并存，接近双倍）。
- 属于重操作，**在业务低峰期做，先备份**。

### 方案 B：在线重建（大表、不停服首选）

```sql
-- 支持在线 DDL，期间允许读写
ALTER TABLE user ENGINE=InnoDB, ALGORITHM=INPLACE, LOCK=NONE;
```

超大表可用 **pt-online-schema-change / gh-ost**（建影子表 + 增量同步 + 切换）做近乎无锁的重建，是线上标准做法。

> 前提：`innodb_file_per_table = ON`（MySQL 5.6+ 默认开），每表独立 `.ibd`，空间才能真正还给系统。共享表空间 `ibdata1` 只增不减，缩不回去。

## 七、从源头预防（比事后整理更重要）

1. **大批量删除改成分批小步删**，避免一次挖出巨大空洞、减轻锁和日志压力：
   ```sql
   DELETE FROM user WHERE create_time < '2023-01-01' LIMIT 10000;
   -- 应用层循环执行，直到删完
   ```

2. **冷热数据分离**：老数据搬到归档表，主表保持精简，不在主表反复删：
   ```sql
   INSERT INTO user_archive SELECT * FROM user WHERE create_time < '2023-01-01';
   DELETE FROM user WHERE create_time < '2023-01-01';
   ```

3. **清空整表用 TRUNCATE**：若是清空而非部分删除，`TRUNCATE` 直接重建文件，立即回收空间、零碎片。

---

## 八、决策流程

```
空洞越来越大?
  │
  ├─ 查 DATA_FREE / 碎片率
  │
  ├─ 碎片率低(<10%) 或 表还在频繁写 ──→ 不用管，会被复用
  │
  ├─ 碎片率高 + 表基本只读 ──→ 低峰期 OPTIMIZE / 在线重建回收
  │
  └─ 以后还会周期性删大批数据 ──→ 从写入/删除模式上预防（分批删、冷热分离）
```

---

## 一句话总结

- **DELETE 不释放磁盘空间**：行被标记删除，空间变成表内可复用空洞，文件大小不变。
- **空洞能否复用看新数据的键值落在哪个页**，不是插入顺序；**自增主键表删中间段，普通 INSERT 永远填不回**。
- 只有**整页空闲**（删空整页或半空页合并）才能被任意新数据复用，但仍不还给操作系统。
- **先查 `DATA_FREE` 量化**，碎片低就别管；要回收用 **`OPTIMIZE TABLE`** 或在线重建，大表低峰期 + 先备份。
- 治本靠预防：**分批删、冷热分离、清空用 TRUNCATE**。
