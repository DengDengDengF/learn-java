# 页与索引扫描：COUNT(*) 为什么走“最小索引”

> 适用引擎：InnoDB。本文解释 `COUNT(*)` 场景下，MySQL 如何在多个索引中挑选扫描对象，以及“页”在其中起的决定性作用。

---

## 一、先搞清楚 InnoDB 的存储单位：页（Page）

InnoDB 不以“行”为单位读写磁盘，而是以**页（page）**为单位。

- 默认页大小 **16KB**（由 `innodb_page_size` 决定）。
- 所有数据（行、索引）都存在页里。
- InnoDB 读任何数据，都必须先把对应的页从磁盘加载到内存的 **Buffer Pool**，再从内存读取。

索引在物理上是一棵 **B+ 树**，由两类页组成：

| 节点类型 | 作用 | 存什么 |
| --- | --- | --- |
| 非叶子节点 | 导航、定位 | 只存 key 和指向下层页的指针 |
| 叶子节点 | 存实际数据，彼此用**双向链表**连接 | 聚簇索引存整行；二级索引存“索引列 + 主键值” |

B+ 树很“矮”，三四层就能支撑千万乃至上亿行，所以**非叶子节点数量极少**。真正占空间、也真正决定扫描成本的是**叶子节点**。

---

## 二、COUNT(*) 为什么必须“全扫一遍”

MyISAM 会直接存一个表总行数，`COUNT(*)` 秒回。

InnoDB 不行：因为 **MVCC**，不同事务在同一时刻看到的行数可能不同，不存在一个“对所有事务都正确”的全局行数。所以 InnoDB 的 `COUNT(*)` 必须**实际遍历一遍索引**，逐行判断可见性后计数。

执行机制：

1. **定位起点**：沿 B+ 树从根往下，走到最左边的叶子页（最小 key 所在处）。这一步只经过少量非叶子节点。
2. **顺叶子链表遍历**：叶子页之间是双向链表，从最左一路顺扫到最右。
3. **逐条计数**：每条记录经过 MVCC 可见性判断，对当前事务可见就 +1。

```
根节点
  └── 中间节点 ...
        └── 叶子页1 ⇄ 叶子页2 ⇄ 叶子页3 ⇄ ... ⇄ 叶子页N   (双向链表)
             ↑最左(最小key)起点，顺链表扫到最右
```

**结论：`COUNT(*)` 本质是 O(N) 全扫描，成本 ≈ 要读的叶子页数量。**

---

## 三、既然必须全扫，就选“扫得最便宜”的索引

优化器的逻辑很朴素：**反正要全扫一遍，那就挑一个要读的页最少的索引来扫。**

### 为什么通常选二级索引，而不是主键（聚簇索引）

- **聚簇索引**叶子节点存**整行数据**，记录很胖，一页装不了几条 → 页数最多。
- **二级索引**叶子节点只存**索引列 + 主键值**，记录很瘦，一页能装几百条 → 页数少得多。

同样数据量，扫二级索引要读的页数远少于扫聚簇索引，IO 更少，所以优化器优先选**窄的二级索引**。

### 叶子页数怎么估

```
叶子页数 ≈ 总行数 × 单条记录宽度 ÷ 16KB
```

- **总行数**：同一张表对所有索引都一样，不影响“选哪个”。
- **单条记录宽度**：这是索引之间拉开差距的关键。索引列越窄（`TINYINT` vs `VARCHAR(100)`），单条越小，一页装得越多，总页数越少。

所以在同一张表里：**“页最少” ≈ “索引列最窄”。**

---

## 四、选中规则：页越少越容易被选中

**核心规律：叶子页越少 → 要读的页越少 → 扫描成本越低 → 越容易被 `COUNT(*)` 选中。**

但要注意三点，避免理解偏差：

1. **优化器真正比较的是“估算成本（cost）”**，页数（IO 次数）是其中最大的因子。绝大多数情况“页最少”就等于“成本最低”，但统计信息不准时偶尔会选错，这属于估算误差，不是规则变了。

2. **前提是该索引能覆盖全表每一行**。页再少，如果数不全全表的行也不会被选。因此要排除：
   - 建在**允许 NULL 列**上的索引（NULL 行可能不进索引，数不全）。
   - 部分/条件索引（MySQL 无此特性，概念上排除）。

   实际规则：在**非空列的二级索引**里挑最窄的；一个都没有，才回退扫聚簇索引。

3. **`COUNT(普通列)` 语义不同**。它要排除该列为 NULL 的行，优化器可能被迫走包含该列的索引，不一定还是最小的那个；若该列可空，结果数也可能和 `COUNT(*)` 不同。

## 五、缓存（Buffer Pool）如何影响表现

`COUNT(*)` 逻辑上要扫全部叶子页，但快不快，很大程度取决于这些页是否已在内存。

```sql
-- 查看 buffer pool 大小（生产常设为物理内存的 50%~70%）
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
```

- **情况 A：索引总大小 < buffer pool 可用空间** → 索引能全部常驻内存。
  `COUNT(*)` 虽仍扫几万个页，但全是内存操作、无磁盘 IO，所以只需几十毫秒。看起来“扛得住”，靠的就是缓存。

- **情况 B：索引大小 > buffer pool，或内存被其他大表抢占** → 缓存放不下。
  LRU 不断淘汰页，扫到后面时前面的页已被挤出，于是**边扫边读盘**，性能退化到磁盘速度，且每次都慢（缓存留不住）。

**关键结论：缓存只能把性能天花板往上抬，抬不动数量级。** 当索引大到无法整体放进 buffer pool 时，再怎么选最小索引、再怎么指望缓存也没用。

## 六、实用验证 SQL

```sql
-- 1) 每个索引多大（粗估，按页大小换算）
SELECT
  INDEX_NAME,
  ROUND(SUM(stat_value) * @@innodb_page_size / 1024 / 1024, 2) AS size_mb
FROM mysql.innodb_index_stats
WHERE TABLE_NAME = 'your_table' AND stat_name = 'size'
GROUP BY INDEX_NAME
ORDER BY size_mb;

-- 2) COUNT(*) 实际选了哪个索引
EXPLAIN SELECT COUNT(*) FROM your_table;
-- 看 key 字段：通常是某个二级索引名（非 PRIMARY）
-- Extra 常见 Using index（覆盖索引，不回表）

-- 3) 表的数据/索引整体大小
SELECT
  TABLE_NAME,
  ROUND(DATA_LENGTH  / 1024 / 1024) AS data_mb,   -- 聚簇索引(数据)
  ROUND(INDEX_LENGTH / 1024 / 1024) AS index_mb   -- 二级索引总和
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'your_db' AND TABLE_NAME = 'your_table';

-- 4) 当前这张表在 buffer pool 里缓存了多少
SELECT
  INDEX_NAME,
  COUNT(*) AS cached_pages,
  ROUND(COUNT(*) * 16 / 1024) AS cached_mb
FROM information_schema.INNODB_BUFFER_PAGE
WHERE TABLE_NAME LIKE '%your_table%'
GROUP BY INDEX_NAME;

-- 5) 整体命中率
SHOW ENGINE INNODB STATUS\G
-- BUFFER POOL AND MEMORY 段里看 "Buffer pool hit rate"
```

## 七、数据量上来后的正确做法

“选最小索引”是 MySQL 无路可走时的省钱策略，不是性能银弹。数据量大到索引放不进内存时，应绕开全扫：

| 需求 | 方案 |
| --- | --- |
| 不需要精确值（列表页“约 N 条”） | 读优化器估算：`EXPLAIN SELECT COUNT(*)` 或 `information_schema.TABLES.TABLE_ROWS` |
| 需要精确值且高频 | 维护计数表，增删时在同事务里 ±1，查询 O(1)（热点可分片累加后 SUM） |
| 带条件计数 `COUNT(*) WHERE ...` | 让 WHERE 走窄的覆盖索引（`Extra` 出现 `Using index`），把扫描范围缩到命中区间 |
| 超大表 + 实时精确 | 交给 Redis 计数器、ClickHouse 等，不让 OLTP 的 MySQL 硬抗 |

---

## 一句话总结

- **页**是 InnoDB 读写和缓存的基本单位（默认 16KB）。
- `COUNT(*)` 必须全扫，成本 ≈ 要读的叶子页数量。
- **“最小索引” = 能覆盖全部行、且叶子页数最少（≈ 索引列最窄）的二级索引。**
- **页越少越容易被选中**，底层判据是“估算成本最低”，页数是主要因子。
- 缓存能抬高天花板但抬不动数量级；真大表要换成估算 / 计数表 / OLAP。
