# MySQL 深度分页优化

一条主线:**深分页慢的根因是 `LIMIT offset` 必须从头「数」够 offset 条才能返回,算法上是 O(n) → 用覆盖索引/延迟关联把每步做轻 → 用游标定位 `WHERE id > ?` 把 O(n) 降成 O(log n) 彻底根治 → 随机跳页是游标的死穴,靠延迟关联 + 产品限制绕开。**

前置心智模型(聚簇索引 B+ 树):主键索引叶子节点存**整行数据**,二级索引叶子节点存**索引字段 + 主键值**。用二级索引查不在索引里的列,要拿主键回主键索引取整行,即**回表**。所查列都在索引里、不用回表,叫**覆盖索引**。

---

## 一、问题:深度分页为什么慢

```sql
SELECT * FROM orders ORDER BY id LIMIT 1000000, 10;
```

MySQL **没法直接跳到第 1000001 条**,只能沿索引从头一条条「数」:

1. 沿 B+ 树叶子节点顺序往后走,读索引项、计数
2. 数够 offset(100 万)条,**前面这些全部丢弃**
3. 只返回之后的 10 条

核心瓶颈:**「数 offset 步」这个遍历动作跑不掉,offset 多大就得挪多少步**,这是 O(n),与返回几条无关。

### 丢弃的行到底回不回表?

| 场景 | 前 offset 条的行为 |
|---|---|
| 走**主键索引**排序(`ORDER BY id`) | 主键叶子就是整行,只读、计数、跳过,只对返回的 10 条取数据 |
| 走**覆盖索引**(查的列都在二级索引里) | 只读索引项、跳过,全程不回表 |
| 走**二级索引但 `SELECT *`**(要的列不在索引里) | 乐观:前面只读索引、仅 10 条回表;悲观:见第二节 |

> 关键:被丢弃的行在主键/覆盖索引下**只数不回表**,MySQL 没傻到把要丢的行也取整行。慢在「数」本身,不在回表。

## 二、`SELECT * ORDER BY 二级索引` 的陷阱

```sql
SELECT * FROM orders ORDER BY create_time LIMIT 1000000, 10;
```

`create_time` 二级索引叶子只有 `(create_time, id)`,`SELECT *` 要的 `amount`、`status` 等列不在里面。优化器有两种执行计划:

- **计划 A(乐观)**:走 `create_time` 索引,前 100 万条只读索引项、不回表,仅最后 10 条回表取整行。
- **计划 B(悲观)**:offset 太大时,优化器算出「走索引再逐条**随机回表**太亏」(整行按主键散乱分布,回表是随机 I/O),**干脆放弃索引**,改成**全表扫描 + filesort**,把整表数据读进来排序再丢弃前 100 万 —— 相当于全表数据都被读了一遍。

**offset 越大,优化器越倾向选 B。这才是深分页的隐藏杀手:不是回表次数多,而是优化器干脆不走索引了。**

用 `EXPLAIN` 判断走的哪个:

- `key` 列:`idx_create_time` 还是 `NULL`(NULL = 没走索引)
- `Extra` 列:出现 `Using filesort` = 在额外排序(计划 B 特征)
- `type` 列:`ALL` = 全表扫描

> 对比:`SELECT id, create_time ...` 因为所查列都在索引里是**覆盖索引**,能顺着二级索引直接「截取」,前面不回表 —— 这正是延迟关联的理论基础。

## 三、解法一:延迟关联(保留跳页能力)

思路:**先只在索引上翻页拿主键(覆盖索引,不回表),再用主键一次性取整行。**

```sql
-- 里层只 SELECT id,是覆盖索引,强制走"纯索引截取",锁死在最优执行计划
SELECT o.*
FROM orders o
INNER JOIN (
    SELECT id FROM orders ORDER BY create_time LIMIT 1000000, 10
) AS t ON o.id = t.id;
```

- 里层 `SELECT id ... ORDER BY create_time`:`id` 和 `create_time` 都在二级索引里 → 覆盖索引 → 前 100 万条只数不回表,也不会退化成全表扫 filesort
- 外层只拿最后 10 个 id 回表取整行 → 只回表 10 次

**没有消除「数 offset 步」(跳页做不到),但把每步做到最轻。** 保留精确跳页能力,改造成本低,是「既要跳页又要快」的标准答案。缺点:offset 极大时里层翻页仍有成本,治标不治本。

## 四、解法二:游标分页 / Seek Method(彻底根治)

思路:**不用 offset,改用「上一页最后一条的 id」做 `WHERE` 定位。**

```sql
-- 第一页
SELECT * FROM orders ORDER BY id LIMIT 10;        -- 末条 id = 10
-- 下一页:直接从 id > 10 开始
SELECT * FROM orders WHERE id > 10 ORDER BY id LIMIT 10;  -- 末条 id = 20
-- 再下一页
SELECT * FROM orders WHERE id > 20 ORDER BY id LIMIT 10;
```

为什么是质变:

```
WHERE id > 1000000 ORDER BY id LIMIT 10

第一步:定位起点 —— O(log n),几次 I/O
   [根] → [非叶子] → [非叶子] → [叶子:id 刚 > 1000000 的位置]
   十亿行也就 3~4 层,且上层节点基本常驻 Buffer Pool

第二步:顺着叶子节点的双向链表往后扫 —— O(limit),只读 10 条
   [1000001][1000002]...[1000010] 够 10 条,停
```

- 不用数 offset 步 ✅(省掉核心瓶颈)
- 不用回表 ✅(主键叶子即整行) / 不用 filesort ✅(主键天然有序) / 顺序 I/O ✅
- **代价与页深无关,翻到第几百万页都一样快**

> 本质:`WHERE id > ?` 是 O(log n) 的 B+ 树查找 + 叶子链表顺序扫;`LIMIT offset` 是 O(n) 的从头遍历。一个 `>` 和 `offset` 的区别,就是 O(log n) 和 O(n) 的区别。这也是 B+ 树所有范围查询(`>`、`BETWEEN`、`ORDER BY`)的通用模式:定位一次 + 顺序扫一段。

缺点:**只能上一页/下一页,不能跳任意第 N 页**(依赖上一页游标)。适合信息流、App 下拉加载。

### 游标分页两个实战细节

1. **排序字段必须唯一**,否则漏/重数据。按非唯一字段排序时拼主键兜底:

```sql
SELECT * FROM orders
WHERE (create_time, id) > ('2024-01-01 10:00:00', 1005)
ORDER BY create_time, id
LIMIT 10;
```

需要 `(create_time, id)` 联合索引支撑,不能只靠主键。

2. **排序字段必须有索引**,否则触发 filesort,优势尽失。
3. id 不连续(删除留空洞)**不影响正确性**,`>` 只是定位起点,顺着往后取 10 条有效记录即可。

## 五、三种写法性能对比

| 写法 | 回表 | filesort | 要数 offset 步 | 评价 |
|---|---|---|---|---|
| `ORDER BY create_time LIMIT 100w,10`(`SELECT *`) | 要,甚至全表扫 | 可能 | 要 | 最差 |
| `ORDER BY id LIMIT 100w,10`(`SELECT *`) | 不用 | 不用 | **还是要** | 好一些,没根治 |
| `WHERE id > ? ORDER BY id LIMIT 10` | 不用 | 不用 | **不用** | 最优 ✅ |

两步优化是独立的:**第一行→第二行**靠「用主键省掉回表 + filesort + 随机 I/O」;**第二行→第三行**靠「用游标定位省掉数 offset 步」。

## 六、随机跳页(游标的死穴)怎么办

游标分页**无法跳任意第 N 页**:点「第 5000 页」时不知道第 4999 页末条 id。而跳页必须「数过前面所有行」,算法上就是 O(offset),**无银弹**。对策分技术层和产品层:

| 真实需求 | 推荐 |
|---|---|
| 信息流 / App / 滚动加载 | 游标分页,不提供跳页 ✅ |
| 后台管理,有页码但很少翻深 | 延迟关联(第三节)+ 限制最大页数 |
| 页码可不精确,只求快 | 主键近似定位(下方) |
| 用户老想翻很深 | **产品层面引导用筛选/搜索** ✅ |

**主键近似定位**(牺牲页码精度换 O(log n)):

```sql
-- 每页 10 条,看第 5000 页,主键自增且删除少、大致连续
SELECT * FROM orders WHERE id >= (5000 - 1) * 10 + 1 ORDER BY id LIMIT 10;
```

直接 B+ 树定位、任意页 O(log n),但有 id 空洞就对不准页码,只适合「大概翻到中间看看」。

**产品层面绕开(大厂最常用)**:深跳页多是伪需求 —— 限制最大页数(如 Google 只给翻几十页)、只给上一页/下一页、用筛选代替翻页(给时间筛选直接缩到几页)。真实需求是「快速找到那条数据」,该用搜索/筛选,不是 5000 个页码。

**总页数也别硬算**:大表 `COUNT(*)` 自身就慢(InnoDB 要扫一遍)。常见处理:显示模糊总数(`EXPLAIN` 的 `rows` 估算 / 计数表),或不显示总数、查 `LIMIT 11` 看有没有第 11 条来判断「还有下一页」。

---

> **一句话收口:深分页慢在 `LIMIT offset` 必须 O(n) 从头数够 offset 条。延迟关联用覆盖索引把每步做到最轻(保留精确跳页),游标分页用 `WHERE id > ?` 做 O(log n) 定位 + 顺序扫彻底根治(但不能跳页)。能接受"不跳页"首选游标;必须随机跳页则延迟关联扛着,并在产品上限制深度、用筛选搜索代替 —— 因为"翻到第 5000 页"几乎总是该被重新设计的伪需求。**
