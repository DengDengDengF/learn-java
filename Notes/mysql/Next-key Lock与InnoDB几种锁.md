# Next-key Lock 与 InnoDB 的几种锁(由浅入深)

> 一条主线:**InnoDB 怎么一步步把「锁」做到既能保证并发安全、又能防住幻读**。
> 从最基础的「读为什么要加锁」讲起,逐层推进到 Record Lock → Gap Lock → Next-key Lock。

---

## 第 0 层:先分清「快照读」和「当前读」——锁从哪来

InnoDB 读数据有两种模式,**只有当前读才加锁**,这是理解后面所有锁的前提。

### 快照读(snapshot read)
普通的 `SELECT ... FROM ...`。读的是**事务开始时的 MVCC 历史快照**,**不加锁**。别人改了你也看不到,所以普通 select 之间互不阻塞。

### 当前读(current read)
读的是**此刻最新的版本**,而且**读的时候就加锁**。以下语句都是当前读:

```sql
SELECT ... FOR UPDATE           -- 加排他锁(X)
SELECT ... LOCK IN SHARE MODE   -- 加共享锁(S)
UPDATE ...                       -- 改之前要先读最新的
DELETE ...
INSERT ...
```

**为什么叫「当前」?** 因为要操作最新数据——你要 UPDATE 一行,不能基于旧快照去改,得看它现在长啥样。既然要动最新数据,就得加锁防别人同时动。

> 后面讲的 Record / Gap / Next-key,全是「当前读」场景下加的锁。

---

## 第 1 层:Record Lock(行锁)——锁住一行

最基础的锁:**锁住一条已经存在的记录(索引记录)**。

```sql
-- id 是主键,这行存在
SELECT * FROM orders WHERE id = 5 FOR UPDATE;
```

事务A 锁住 id=5 这行,事务B 想 UPDATE/DELETE 这行就得等。

**特点:**
- 锁的是**索引上的一条具体记录**。
- 只能锁**已存在**的行。
- 这是粒度最细、并发最好的锁。

**局限:它锁不住「还不存在的行」。** 这正是下一层要解决的问题。

---

## 第 2 层:幻读——行锁为什么不够

假设你在一个事务里要锁住所有 amount > 100 的订单来处理:

```sql
-- 事务A
SELECT * FROM orders WHERE amount > 100 FOR UPDATE;
-- 查到 3 行,用行锁锁住
```

这时事务B 插入一行新数据并提交:

```sql
-- 事务B
INSERT INTO orders (amount) VALUES (200);  -- 200 也满足 amount > 100
```

事务A 再查一次,**凭空多出来一行**。

> **幻读(phantom read):事务把「符合条件的已有行」都锁住了,却挡不住别人「新增」一行符合条件的数据。**

根本原因:**行锁只能锁已经存在的行,新增的行本来不存在,行锁够不着。** 要堵住「新增」,必须锁住「行与行之间的空隙」。

---

## 第 3 层:Gap Lock(间隙锁)——锁住空隙

Gap Lock 锁的不是行,而是**两条记录之间的空隙(开区间)**,目的就是**阻止别人往这个空隙里 INSERT**。

假设 amount 列有索引,现有值:

```
50, 100, 150, 200
```

这些值把数轴切成若干间隙:

```
(-∞,50)  (50,100)  (100,150)  (150,200)  (200,+∞)
```

如果某个间隙被 Gap Lock 锁住,比如 `(100, 150)`,那别人想 `INSERT amount = 120`(落在这个空隙里)就会被阻塞。

**特点:**
- 锁的是**范围/空隙**,不是具体的行。
- 只防新增(INSERT),**不阻止对已有行的读写**(它本来就不锁行)。
- Gap Lock 之间**不互斥**:两个事务可以同时持有同一个间隙的 Gap Lock(因为它们只是都「不希望这里被插入」,不冲突)。

---

## 第 4 层:Next-key Lock(临键锁)——行锁 + 间隙锁的组合

这是 InnoDB 在 **RR(可重复读)隔离级别下的默认行锁算法**,也是防幻读的主力。

> **Next-key Lock = Record Lock(行锁) + Gap Lock(间隙锁)**
> 锁住的是一个**左开右闭的区间 `(前一个值, 当前值]`**——既锁住这一行,也锁住它前面的空隙。

### 完整例子

amount 有索引,现有值 `50, 100, 150, 200`。事务A 执行:

```sql
SELECT * FROM orders WHERE amount > 100 FOR UPDATE;
```

InnoDB 会加上这些 Next-key Lock 区间:

```
(100, 150]    (150, 200]    (200, +∞)
```

注意最后的 `(200, +∞)`——**把 200 之后的所有空隙都锁了**。

现在事务B 想 `INSERT amount = 300`:

- 300 落在被锁的 `(200, +∞)` 区间里
- 这个区间被事务A 占着
- → **事务B 的 INSERT 被阻塞**,直到事务A 提交释放锁

幻读就这样被堵住了:

> **当前读(FOR UPDATE)触发加锁 → Next-key Lock 锁住一段范围(含间隙)→ 别人往这段范围 INSERT 新行被挡住 → 防止幻读。**

---

## 第 5 层:四种锁对比总表

| 锁类型 | 锁什么 | 能锁已有行吗 | 能防新增吗 | 典型场景 |
|---|---|---|---|---|
| **Record Lock(行锁)** | 单条已存在的记录 | ✅ | ❌ | 唯一索引等值命中 |
| **Gap Lock(间隙锁)** | 两行之间的空隙(开区间) | ❌ | ✅ | 防止范围内插入 |
| **Next-key Lock(临键锁)** | 行 + 前面的空隙(左开右闭 `(x, y]`) | ✅ | ✅ | RR 下的默认,范围查询 |
| **Insert Intention Lock(插入意向锁)** | 间隙内「打算插入」的位置 | —— | —— | INSERT 前的特殊间隙锁,多个插入不冲突时可并发 |

> 记忆:**Record 锁点,Gap 锁缝,Next-key 锁「点+缝」。**

---

## 第 6 层:关键提醒(踩坑点)

### 1. 只有 RR 隔离级别才有 Next-key Lock 防幻读
- **RR(可重复读,MySQL 默认)**:用 Next-key Lock,防幻读。
- **RC(读已提交)**:基本退化为只用 Record Lock,**没有间隙锁,不防幻读**。
- 隔离级别的选择直接决定了用哪些锁。

### 2. 走不走索引,决定锁的范围大小
- 条件**走了索引**:只锁命中的区间,范围小,并发好。
- 条件**没走索引**:InnoDB 要扫全表,进而**锁住几乎所有行和间隙**(接近锁全表),并发直接崩溃。

> **索引不仅影响查询速度,还直接决定加锁范围。** 这是「索引」和「锁」两个话题真正打通的地方。

### 3. 等值命中时 Next-key Lock 会「退化」
InnoDB 做了优化,不是任何情况都锁一整段:
- **唯一索引等值查询且命中**:退化为 **Record Lock**(只锁那一行,不要间隙)。
- **唯一索引等值查询但未命中**:退化为 **Gap Lock**(锁那个不存在值所在的间隙,防别人插进来)。
- 范围查询才用完整的 Next-key Lock。

### 4. 间隙锁容易引发死锁
两个事务互相锁住对方想插入的间隙,是生产中常见的死锁来源。排查死锁时优先怀疑间隙锁。

---

## 一句话总结

InnoDB 的锁是**层层加码**解决并发问题的:**行锁(Record)** 保证单行安全,但挡不住新增;于是有了 **间隙锁(Gap)** 专门锁空隙防插入;两者合体成 **Next-key Lock**,在 RR 级别下既锁行又锁缝,最终堵住幻读。而这套锁锁得「准不准、大不大」,很大程度上取决于**查询有没有走好索引**。
