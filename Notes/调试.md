# Resume 和 StepOver

| 对比维度                  | **Resume (F9)**                                              | **Step Over (F8)**                                           |
| :------------------------ | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **指令性质**              | **异步触发（Fire-and-Forget）** “你全速跑，跑完了或者撞到断点再叫我。” | **同步等待（Wait-and-Reply）** “你执行完这一行，**必须**把控制权还给我，停到下一行。” |
| **遇到 I/O 阻塞时的表现** | **UI 流畅，按钮可用** 线程被操作系统挂起，但 IDE 不管了，继续干自己的事。 | **UI 完全卡死，按钮全灰** IDE 傻等操作系统回复，结果操作系统永远不回复（没数据/连接），IDE 界面被“冻住”。 |
| **对其他线程的影响**      | **无影响** 其他线程照常运行，IDE 依然能响应点击。            | **通道堵塞** IDE 的调试命令通道被当前 F8 请求占满，切到其他线程按 F8 也没反应。 |
| **焦点/线程切换**         | **自动跟随命中断点的线程** 一旦任何线程撞上断点，IDE 立马把镜头切过去。 | **无法切换** 界面卡死，连切换线程查看状态都做不到（或极其滞后）。 |
| **如何“推进”代码**        | **靠外部事件推进**（浏览器发数据 / 新连接 / 超时） 事件发生后，线程自动越过阻塞，跑向断点。 | **原地等死** 除非外部事件发生，否则永远停在这一行，永远无法进入下一行。 |
| **适用场景**              | **专门用来“跨过” I/O 阻塞** `accept`、`readLine`、`sleep` 统统点它。 | **只用于“纯计算/内存”操作** 赋值、加减乘除、字符串拼接、普通方法调用。 |

| 当前光标所在行                                  | 按什么键                     | 千万别按         |
| :---------------------------------------------- | :--------------------------- | :--------------- |
| `ss.accept()` / `readLine()` / `Thread.sleep()` | **Resume (F9)**              | ❌ Step Over (F8) |
| `int a = b + c;` / `System.out.println(...)`    | **Step Over (F8)** 或 Resume | 都行，但 F8 更细 |

**终极心法**：看到代码里有 **`wait`、`accept`、`read`、`sleep`** 这些字眼，**立刻把手从 F8 挪开，只按 F9**。遇到断点后进入方法内部，再放心地用 F8 逐行看业务逻辑。
