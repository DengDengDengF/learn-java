# MySQL InnoDB 事务日志与 MVCC

一条主线:**redo log 保证不丢 → undo log 保证能回滚 + 存旧版本 → 隐藏字段把旧版本串成链 → ReadView 决定每次读看哪个版本。**

---

## 一、redo log（重做日志）

解决「已提交的事务不能丢」(持久性)。

- InnoDB 改数据是先改内存(Buffer Pool)里的数据页,不立刻刷盘(随机 I/O 太慢)。
- 改动先用**顺序写**记进 redo log,只要 redo log 落盘就算安全 —— 这就是 **WAL(预写日志)**:先写日志,再刷数据页。
- 崩溃重启时,扫描 redo log 把「还没刷进数据页的修改」重做一遍,数据恢复到崩溃前。
- 特点:**物理日志**(记录某页某位置做了什么物理修改)、**固定大小循环写**。
- 刷盘策略 `innodb_flush_log_at_trx_commit`:`1`(默认,每次提交都刷,最安全) / `0`(每秒刷,崩溃丢1秒) / `2`(折中)。

---

## 二、undo log（回滚日志）

解决两件事:**回滚**(原子性)和 **MVCC(**`Multi-Version Concurrency Control`**) 读旧版本**(隔离性)。

- 每次修改前,先把**旧值**记进 undo log(INSERT 记逆删除、DELETE 记逆插入、UPDATE 记旧值)。
- `ROLLBACK` 或崩溃时,用 undo log 反向还原。
- 提交后 undo 不能立即删:可能还有更早的事务要靠它读旧版本,由后台 **purge 线程**在无人依赖后清理。**长事务会导致 undo 堆积膨胀**。
- 特点:**逻辑日志**(记录逆向操作)。

---

## 三、行里的隐藏字段

每行除了用户列,InnoDB 还加三个隐藏字段:

| 字段 | 大小 | 作用 |
|------|------|------|
| `DB_ROW_ID` | 6B | 没有主键/唯一非空索引时的兜底隐藏主键 |
| `DB_TRX_ID` | 6B | 最后修改这行的**事务 ID**(事务 ID 全局单调递增) |
| `DB_ROLL_PTR` | 7B | **回滚指针**,指向 undo log 里这行的上一个版本 |

`DB_TRX_ID` 回答「谁最后改的我」,`DB_ROLL_PTR` 回答「我的上一版在哪」。

### 版本链

每改一次:旧值进 undo → 新行的 `DB_ROLL_PTR` 指向那个旧版本 → `DB_TRX_ID` 更新为当前事务。
一行被改多次后,靠回滚指针串成一条**从新到旧的版本链**:

```
当前行 v3 (TRX_ID=300) ──ROLL_PTR──▶ v2 (TRX_ID=200) ──ROLL_PTR──▶ v1 (TRX_ID=100) ──▶ NULL
```

用途:回滚沿链还原;快照读沿链找「对我可见」的版本。

---

## 四、ReadView(读视图)

快照读时,靠 ReadView 判断版本链上哪个版本对自己可见。它是一个**时间点快照**,冻结了「生成它那一刻,哪些事务已提交、哪些还活跃」。

四个关键值:

| 字段 | 含义 |
|------|------|
| `m_ids` | 生成时仍**活跃(未提交)**的事务 ID 列表 |
| `min_trx_id` | `m_ids` 里的最小值 |
| `max_trx_id` | 系统下一个将分配的事务 ID |
| `creator_trx_id` | 创建这个 ReadView 的事务自己的 ID |

### 可见性判定(拿版本的 `DB_TRX_ID` 比)

1. `== creator_trx_id` → 自己改的 → **可见**
2. `< min_trx_id` → 生成前已提交 → **可见**
3. `>= max_trx_id` → 生成后才开启 → **不可见**,沿链找旧版本
4. `min_trx_id <= trx_id < max_trx_id`:在 `m_ids` 里 → 当时没提交 → **不可见**;不在 → 已提交 → **可见**

不可见就用 `DB_ROLL_PTR` 跳到更旧版本,重复判定,直到找到可见的。

## 五、RC 与 RR 的唯一区别:ReadView 多久建一次

机制、版本链、隐藏字段都一样,**唯一差别是 ReadView 的生成时机**。

**一个事务里做 N 次快照读,产生几个 ReadView?**

| 隔离级别 | ReadView 数量 | 参照时间点 | 结果 |
|---|---|---|---|
| **RC**(读已提交) | **每次读新建,N 次 = N 个** | 每次都是「本次读的时刻」 | 别人中途提交的能看到 → **不可重复读** |
| **RR**(可重复读,默认) | **只第一次读建,全程 1 个** | 钉死在「第一次读的时刻」 | 别人中途提交的看不到 → **可重复读** |

补充:

- N 指**快照读次数(执行几次 SELECT)**,一条 SELECT 返回多少行都只用 1 副。
- ReadView 是**用到才建**:RR 下如果整个事务没做过快照读,一个 ReadView 都不生成,触发点是「第一次快照读」而非 `begin`。

本质一句:**判定规则两者相同,差别只在参照的时间点会不会移动 —— RC 每读一次往前挪一次,RR 整个事务钉死在第一次读。**

## 附:一次 UPDATE 的全景(含 binlog)

```
1. 数据页加载到 Buffer Pool
2. 旧值写入 undo log        ← 为回滚 / MVCC
3. 内存改为新值             ← 产生脏页
4. 写 redo log,状态 prepare
5. 写 binlog(Server 层,主从复制/恢复用)
6. 提交,redo log 改为 commit ← 两阶段提交,保证 redo 与 binlog 一致
```

> redo/undo 属 **InnoDB 引擎层**(解决单机崩溃恢复与事务);binlog 属 **MySQL Server 层**(主从复制、按时间点恢复)。
